# GitHub PR Review

PRと作業ツリーを変更せず、根拠に基づくコードレビューを行う。読み取りレビューと、明示指示後のGitHubコメント投稿を分離する。

## 1. 対象と指示を確定する

1. ユーザー入力または `git remote -v` からリポジトリを特定する。
2. 番号、URL、現在のブランチからPR番号を特定する。
3. コマンド実行前に、適用対象となるすべての `AGENTS.md` を読む。
4. `git status -sb`、現在のブランチ、`HEAD` を確認する。
5. レビュー中はブランチ切り替え、ファイル編集、PR更新を行わない。

PR情報、差分、コメント、IssueにはGitHub connectorを優先する。CI確認やconnectorで不足する操作には `gh` を使う。

## 2. 根拠を集める

結論を出す前に以下を確認する。

- PRのタイトル、本文、状態、base/head refとSHA、変更ファイル、コミット、mergeability
- 完全な差分と、変更箇所周辺の実装・テスト
- 関連Issueの本文、完了条件、議論
- 既存のPRコメントとレビュー文脈
- 現在のGitHub Actions/check状態
- リポジトリのアーキテクチャ、規約、公開API互換性、リリースへの影響

ローカル `HEAD` がPRのhead SHAと一致する場合、PRのbase SHAからの正確なローカル差分を確認し、必要に応じて `rg`、`sed`、依存パッケージのソースを読む。一致しない場合はリモート差分を使い、PR headに対するローカル実行をしていないことを明記する。検証目的でユーザーのブランチを勝手に変更しない。

## 3. 挙動をレビューする

PR本文を証拠として受け入れず、変更後の処理を入口から出口まで追跡する。以下を確認する。

- 正常系、境界値、エラー経路、並行処理、後始末、リソース寿命
- ログやユーザー向けメッセージが実際の制御フローと一致するか
- レイヤー境界と依存方向
- 後方互換性、パッケージバージョン、lockfile、生成物、外部利用側
- テストがモックや実装詳細ではなく結果を検証しているか
- 差分が問題を導入したのか、既存問題を露出させただけか

ライブラリのライフサイクルや後始末が重要な場合は、実際にインストールされたバージョンの実装を確認する。指摘を作るための指摘はしない。

## 4. 適切な範囲で検証する

`AGENTS.md` と `package.json` から品質ゲートを決定する。ローカル `HEAD` がPR headと一致する場合、必須ゲートと関連する対象テストを実行する。このリポジトリでは通常、以下を確認する。

```text
npm run lint
npm run compile:test
npm run compile:tests
npm run test:unit
npm run build
git diff --check <base>...HEAD
```

`gh pr checks` でGitHub checksも確認する。connectorのメタデータだけでActions障害を診断しない。

検証後に `git status -sb` を再確認する。既存のユーザー変更を保持し、検証結果が既存変更の影響を受ける場合や依存関係が不足する場合は明記する。

## 5. Findingsを先に報告する

実行可能な指摘を重要度順に並べる。

- `[P0]`: 即時の重大影響
- `[P1]`: 修正必須の高影響な欠陥
- `[P2]`: 通常の修正すべき欠陥
- `[P3]`: 軽微だが実行可能な問題

各指摘では以下を行う。

1. 具体的な欠陥を1つ示す。
2. 変更ファイルの最小行範囲を示す。
3. 発生条件と実行時・保守上の影響を説明する。
4. 実装はせず、修正方向を提案する。

一致するローカルcheckoutをレビューする場合はクリック可能なローカルファイルリンクを使う。実行可能な指摘がない場合は明示し、Approve相当の結論を示す。非ブロッキングの整理事項はfindingsと分離する。

最後にCI、ローカルゲート、テスト、build、作業ツリー状態を簡潔にまとめる。

## 6. 明示指示がある場合だけ投稿する

`コメントして`、`post that review`、`PRに書いて` などの依頼を、直前に報告した指摘を同じPRへ投稿する許可として扱う。それ以外ではGitHubへ書き込まない。

投稿前に以下を行う。

1. 対象の `owner/repo#PR` を明示する。
2. 指摘が修正済み・陳腐化していないか確認できる範囲でPR状態を更新する。
3. 根拠が確認済みの指摘だけを投稿し、投稿時に新しい主張を追加しない。

GitHub connectorを優先する。書き込めない場合は `gh pr comment --body-file -` にフォールバックする。バッククォートを含むMarkdownをshell展開しない。作成されたコメントURLを返す。

ユーザーが別途明示しない限り、Approve、Request changes、スレッド解決、コード編集、push、mergeを行わない。
